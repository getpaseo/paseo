# Goals

A Goal is one objective that Paseo plans, carries out with several coding agents, reviews, tests and merges on its own branch. You start it once and read the result from the history.

## Roles

| Role     | What it is                                                                                                                                                                                                                                                                                                           |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Manager  | Daemon code, no model. Schedules tasks, records events, retries, enforces limits and recovers after a restart. `packages/server/src/server/goal/`.                                                                                                                                                                   |
| Lead     | An agent that reads the repository, proposes the plan and can revise it while it runs. It is also the conversation: the Manager messages it about failures and completion, asks it what to do when a task times out or keeps failing, and checks in with it about a worker whose run nears its time limit or stalls. |
| Workers  | Agents that carry out tasks, each in its own worktree, on the task's provider or the goal's default.                                                                                                                                                                                                                 |
| Reviewer | A fresh agent that reads one change and returns approve or request changes. It never wrote the change.                                                                                                                                                                                                               |
| Verifier | A fresh agent that checks each acceptance criterion against the merged result and gives evidence.                                                                                                                                                                                                                    |

Agents reason and edit. The Manager decides what runs, in what order, and what counts as done. The reducer (`goal-reducer.ts`) rejects any event that breaks the rules below, so a Manager bug cannot write an illegal state to the log.

## Start one

```bash
paseo goal create "Add rate limiting" \
  --objective "Limit the public API to 100 requests a minute per key" \
  --criterion "Requests over the limit get HTTP 429" \
  --criterion "Existing API tests still pass" \
  --cwd ~/code/api --lead claude --provider codex \
  --review-provider opencode --test-command "npm test" --auto-approve

paseo goal ls                     # --search, --status, --priority, --archived, --project
paseo goal inspect <id>           # tasks and their status, plan revisions
paseo goal changes <id>           # change sets and where each stands
paseo goal notifications <id>     # messages to the Lead and the chat, and their outcome
paseo goal inspect <id> --json    # full goal and event history
paseo goal reject-plan <id> --message "Split the migration out"
paseo goal revise <id> --file revision.json   # change a running plan
paseo goal approve-revision <id>  # or reject-revision <id> --message ...
paseo goal pause <id>             # start no new worker runs
paseo goal resume <id>
paseo goal retry <id>             # retry failed tasks or a failed merge; reopens a failed goal
paseo goal diagnose <id>          # why a failed goal stopped and what it needs
paseo goal recover <id> --prompt "..."   # a fresh Lead decides how a failed goal goes on
paseo goal accept <id> --note "..."      # complete a failed goal as is, waiving unmet criteria
paseo goal config <id> --on-permission wait --max-runs 100   # change settings
paseo goal cancel <id>
paseo goal ack <id>               # dismiss an ended goal
paseo goal rename <id> "New title"
paseo goal priority <id> high     # low, normal or high
paseo goal archive <id>           # hide an ended goal from goal ls
paseo goal unarchive <id>
paseo goal delete <id> [--yes]    # remove an ended goal for good
```

`paseo goal ls` shows each goal's progress, elapsed time, reported usage and what it is waiting on. `paseo goal inspect` shows the same per task, and `paseo goal inspect <id> --usage` lists usage per agent, per role and in total.

Without `--cwd` the goal is manual: it records plans and state and nothing runs. With `--cwd` the Manager takes over. `--cwd` must be a git repository.

## Lifecycle

1. **Plan.** The Lead replies with a JSON task graph: ids, titles, descriptions, kinds (`implement`, `review`, `read`), dependencies, optional providers, optional `thinking` and an optional `runTimeoutMinutes`. The Manager checks it (no cycles, known providers, thinking ids the task's model lists, within the task limit, no ids ending in `-rw<n>`) and sends an unusable plan back, up to two times.
2. **Approve.** The goal waits for `paseo goal approve <id>`, or approves itself with `--auto-approve`. `paseo goal reject-plan <id> --message ...` sends the plan back instead: the Lead and its worktree are retired, and a new Lead plans with your feedback and the rejected plan in its prompt. A plan can be rejected 5 times.
3. **Execute.** Ready tasks start, at most `maxParallel` per goal and `daemon.goals.maxConcurrentRuns` (default 4) across the daemon; when the daemon is full, a freed slot goes to the highest-priority goal with a ready task. Each task gets its own worktree. A task runs on its own provider or the goal's default. Its prompt includes the reports of the tasks it depends on. A failed task is retried after a backoff, up to `maxAttempts` failed attempts; a timeout, a second failure or the last attempt first asks the Lead (see [Lead decisions](#control-a-running-goal)). A run interrupted by a restart does not count as a failed attempt. A run that stopped on a request nobody could answer is not retried; see [Security model](#security-model). A worker that ends with a blocked status line is not retried either; see [Worker status line](#security-model).
4. **Capture.** When an implement task succeeds, its work is committed if needed and recorded as a change set with explicit base and head commits and the changed files. A task that changed nothing is recorded as such.
5. **Review.** A reviewer reads `git diff base..head` in the author's worktree. Changes it asks for, merge conflicts and test failures each become a rework task that continues in the author's worktree, up to `maxReworkRounds`. A rework that fails for good rejects the change set and fails the goal; retry reworks it (see [Retry a failed rework](#control-a-running-goal)).
6. **Integrate.** Approved change sets merge one at a time into the goal's integration branch in its own worktree. The branch is `<branchPrefix>/<goalId>`, `paseo-goal/<goalId>` by default, and Paseo's branch auto-namer is told to leave it alone. Its worktree path is in `paseo goal changes <id> --json`. `testCommand`, if set, runs after each merge; a failure resets the branch. A merge is refused while a tracked file in the integration worktree has uncommitted changes. Untracked files do not block it: tools leave caches and state directories there (a `.gjc/` directory once failed a goal this way), and `git merge` itself refuses a merge that would overwrite an untracked file. Either refusal, or any other error in the merge step, resets the integration worktree (`reset --hard`, `clean -fd`), rejects the change set with `rejectionReason: "integration_failed"` and fails the goal; retry merges it again.
7. **Verify.** When everything is integrated, the verifier checks each acceptance criterion and records its evidence. Only then does the goal complete.

An implement task that depends on another starts only after that task's change set is integrated, and branches from the integrated commit, so it builds on the merged code. Each such dependency therefore waits for review, any rework rounds, the merge and, under `requireHumanApproval`, you. A plan whose tail is a chain of dependent tasks runs one task at a time however many slots are free; the Lead's prompt asks it for independent tasks split by files or areas, only the dependencies a task needs, a short tail after any fan-in task, and the critical path in its explanation. The plan check rejects cycles, unknown ids and too many tasks; it does not limit how wide or deep a plan is.

The result is the integration branch and its worktree. Nothing is merged into your branch or pushed. Review it and merge it yourself.

## What is guaranteed

- **No unreviewed merge.** A change set can reach `integrating` only from `approved`, and `approved` only from a reviewer's verdict or your approval. The transition table in the reducer enforces it. Before each merge the pipeline also checks that the integration branch is where it left it, and resets it if something else moved it. Agents share the repository's git data, so a misbehaving agent could still try to write there; the checks catch that, they cannot stop it.
- **No early completion.** The reducer refuses `goal.completed` while a change set is neither integrated nor superseded, an implement task's work was never captured, or a criterion is unverified. A managed goal needs at least one criterion. The one way to complete with an unverified criterion is a person's [accept](#control-a-running-goal), which records each such criterion as waived.
- **Your checkout is never touched.** Every agent, including the Lead, works in its own worktree. The integration branch is separate from your branches. Every worktree waits for its `paseo.json` setup to finish (up to 5 minutes) before an agent or a merge uses it. Worktrees start from the commit that was checked out in `cwd` when the goal was created, recorded as `baseCommit`, so a goal started on a feature branch builds on it. `goal.create` also takes a `config.baseCommit` to build on instead, such as a failed goal's integration head. It must be a commit id of at least 7 hex digits that the repository at `cwd` has; a branch or tag name is refused even when it looks like hex, so the base cannot move later. It is stored in full.
- **Restarts lose nothing.** State is an append-only event log. After a restart, interrupted runs are closed out as interrupted and run again, and an interrupted run does not use up an attempt. A daemon that keeps crashing is bounded by `maxRuns`. A test restarts the daemon after each event of a full scenario and requires the goal to finish.
- **Every notification has a recorded outcome.** A message to the Lead (a task failed for good, the goal completed) or to the originating chat (how the goal ended) is recorded before it is sent, with its text, and each attempt is recorded as delivered or failed. A failed attempt is retried after 5 seconds, then 30, 120 and 300, five attempts in all; after the fifth failure the notification stays `failed` with its last error. Delivered means the agent layer accepted the prompt, not that anyone read it. After a goal has ended, only notifications, an acknowledgement, a rename, a priority change, a settings change, archiving, a retry that reopens it, a recovery and an accept are accepted.
- **Duplicates do nothing.** An event id is recorded once. Resending a request with the same `eventId` returns the existing result.

## Control a running goal

- **Pause.** `paseo goal pause` stops new worker runs from starting. Runs already going finish and are recorded; their reviews, merges and rework scheduling continue. Nothing new starts, and the goal is neither verified nor failed for being stuck until you resume. Planning and plan approval still happen. Time, run and budget limits keep counting. The pause is an event, so it holds across restarts: interrupted runs are closed out and wait as pending tasks.
- **Retry.** `paseo goal retry <id> [--task <taskId>]` returns failed or cancelled tasks to pending. Their earlier failed runs stop counting against `maxAttempts`, so each gets a full set of attempts again; the run limit and budgets do not reset, and the time limit restarts only as the retry chooses (below). On a live goal you can name one task. A failed goal is reopened to executing and every failed and cancelled task is retried, because one left behind would fail the goal again at once. A failed goal is not reopened when a change set was rejected by review (the reviewer, the rework limit or a rework that changed nothing; the goal can no longer complete), the run limit, deadline or a budget is used up, or nothing failed (a verification failure: recover it instead, below). Retry also waits until the failed goal's stopping agents have ended. After reopening, change sets are picked up where the failure left them, as after a restart, and the chat that started the goal is told about its next ending as well. `--prompt` and `--task-prompt <taskId>=<text>` give the workers your instruction, as on recover (below); a retry that reopens planning or merges a failed change set again takes none.
- **Time limit on retry.** The time limit is wall-clock time: pausing does not stop it, and neither does sitting failed. Only time spent [waiting for an answer](#security-model) is left out. A retry, merge retry or planning reopen after it has passed is refused unless it says how the limit restarts. `fresh` (`paseo goal retry <id> --time fresh`) counts the full limit from the retry. `remaining` gives the limit minus the time the goal ran since creation or the last `fresh`; it is the only mode that leaves paused and failed time out, and it is refused when no time is left. The daemon reads the running time from the log and records it on the event, so a replay sets the same base (`timeBaseAt`), and a later limit edit moves the deadline from it. Without a mode the limit counts as before. No mode moves `limits.deadlineAt`; once that has passed, set a later one or clear it. Budgets stay cumulative, because tokens and cost already spent stay spent. On a terminal, `goal retry` asks which mode; with `--json` or no terminal it needs `--time`. The app's Retry opens the same choice; in the goal detail it shows how much time `remaining` would leave.
- **Retry a failed merge.** A change set whose merge step failed is rejected with `rejectionReason: "integration_failed"` (the transition's `reason`; a log written before v0.13.10 is read from the `Integration failed` error text of a rejection out of `integrating`). `retry` on its failed goal records one `changeset.integration_retried`: every such change set goes back to `approved`, oldest first, and every failed and cancelled task is retried with it, as in any reopen. Its review and your approval stand, so nothing is reviewed again; the merges run one at a time as usual. The goal is reopened as above: `reopens` goes up, the failure reason is cleared, the limits must leave room and the deadline is re-armed. One event does both, so a crash cannot leave a reopened goal with the change set still rejected. A goal that also has a change set rejected by review is not reopened. With nothing to retry, the error says so: `no failed or cancelled task, no change set rejected by a failed integration and no failed rework`.
- **Retry a failed rework.** A change set whose rework task failed for good is rejected with `rejectionReason: "rework_failed"`; a log written before v0.13.14 is read from the `Rework <task> failed: ` error of a rejection out of `changes_requested`, `conflicted` or `test_failed`. A retry or recovery that reopens the goal lists every such change set as `reworkChangeSetIds` on its event: each goes back to the status it was rejected from, with its round, findings and worktree, and its rework task runs again with its failures forgiven. When two reworks fail together, the Manager rejects the first and fails the goal; the other change set still waits for its rework, whose task the same retry runs again. `paseo goal retry` prints `Reopens the rework of <change set> (task <id>)` for each. Rounds do not reset, so a reviewer who asks for changes again after the last round ends the change set at the rework limit, which is final. The rework runs in the change set's own worktree, so a retry or recovery is refused while that worktree is gone. The refusal names the change set's branch, which still holds its work, since Paseo never deletes branches: start a new goal from the integration branch and rebuild the change from that branch. A recovery's revise cannot replace a rework task, so it cannot get around this. The check looks for the directory, so a worktree archived in Paseo whose directory was kept still passes it. A rework that stopped on a request fails the goal with `stopped on a request (needs_permission)`, as any task does: change the policy with `goal config` before retrying, or the same request stops it again. The daemon fills `reworkChangeSetIds` from the goal; clients never send them. The other rejections stay final: the rework limit (`rejectionReason: "rework_limit"`, recorded from v0.13.14; older logs carry no reason for it), a rework that added no commits, a rework task that could not be added, and a review that failed.
- **Reopen a planning failure.** A goal that failed before it had a plan (the Lead asked for a permission under `fail`, stopped, or gave no usable plan) has no tasks. `retry` on it, without `--task`, records `goal.reopened`: the goal goes back to planning with the same config, `reopens` goes up and the failure reason is cleared, and a fresh Lead plans in a new worktree, as at creation. The earlier Lead stays in the history as its own `lead.attached`. The run limit, time limit and budgets must leave room, as for any reopen. Change the setting that caused the failure first, for example `paseo goal config <id> --on-permission wait`.
- **Recover a failed goal.** Use it when a plain retry would fail the same way.
  1. `paseo goal diagnose <id>` says why the goal stopped: each failed task's cause, what it blocks, the limits that leave no room with the smallest values that would, and whether a person must act. The app shows the same diagnosis.
  2. Raise a blocking limit with `paseo goal config` first. Nothing raises one for you, not the Lead and not `recover`.
  3. `paseo goal recover <id> [--prompt "..."] [--task t7="..."] [--time fresh|remaining]` (`goal.recovery.start`) checks the integration worktree, then gives the goal a fresh Lead in a worktree at the integration head. The goal stays failed while the Lead decides, for at most 20 minutes.
  4. The Lead answers once, with one of the decisions below. A revise without `autoApprovePlan` waits for `paseo goal recover <id> --approve`, or `--reject [--message ...]`, which leaves the goal failed.
  5. The decision is applied and the goal executes again. Succeeded tasks and merged work stay; the recovery neither moves nor resets the integration branch.

  | Decision                             | What happens                                                                                                                       |
  | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
  | `retry`                              | Every failed and cancelled task runs again with its failures forgiven, optionally with the Lead's advice for named tasks' workers. |
  | `revise`                             | A plan change, recorded as the Lead's plan revision (it counts toward that limit), then the same retry.                            |
  | `needs_person`                       | The recovery ends; the goal stays failed with the Lead's reason, such as the setting to raise.                                     |
  | no usable answer in time, or no Lead | The failed tasks are retried with your instruction only.                                                                           |
  - **Your instruction.** `--prompt` and `--task` text is authoritative: the Lead and the workers get it as your instruction, it stays for later runs, and an empty text (`--task t7=`) clears it. The Lead's advice reaches only the tasks it names, as another agent's advice, until the next recovery replaces it.
  - **Time.** `--time` works as on retry, except that the limit restarts when the recovery is applied, so time spent deciding or waiting for your approval is not charged.
  - **The integration worktree** must exist, sit at the commit the goal recorded, and have no uncommitted changes to tracked files. `recover` is refused otherwise, with the path, the commit and the command to run. The daemon checks again after a restart and before applying; a problem then ends the recovery the same way.
  - **Limit.** A goal counts at most 3 recoveries. One counts once its Lead decided, whether it applied or you rejected it; it does not count when it fell back, was cancelled, or stopped on the integration check or a limit.
  - **While one is open**, retry, archive, delete and another recovery are refused. `paseo goal recover <id> --cancel` stops it, except in the moment it is being applied.
  - **When it ends without applying**, the chat that started the goal is told and the recovery's Lead is stopped and archived. Once applied, that Lead stays the goal's Lead.
  - A goal with a change set rejected by review cannot be recovered in place. A failed merge is merged again and a failed rework is reworked again, as on retry; the rework's worktree is checked with the integration worktree.
  - **A failed verification** (every task succeeded, a criterion was not met) is recovered by a revise that adds fix tasks. The Lead sees each criterion marked verified, not met, or not verified when verification did not finish (then a retry asks the verifier again); the verifier's evidence is in the failure reason. A recovery that adds or replaces a task once verification has started, or after a deadline cut it short, clears every criterion when it applies and starts a new verification round (`verificationRound`, shown by `paseo goal inspect`). The fix tasks run, are reviewed and merged first; then the verifier checks every criterion again, including those it passed before, against the new code. The earlier results stay in the log. A retry, or a revise that only removes tasks, keeps the results and asks only about the unmet criteria, on unchanged code. Outside a recovery, revisions stay refused once verification has started. With no recovery left, `diagnose` says a person must decide: accept the goal as is (below) or start a follow-up goal from the integration branch.

- **Accept as is.** `paseo goal accept <id> --note "..."` (`goal.outcome.accept`) completes a failed goal whose work is all done and merged although some criteria are not verified, when you judge the result good enough, for example once no recovery is left after a failed verification. The app offers it in the failed goal's banner.
  - It waives every criterion still unverified at once; waiving only some is not supported. The note is required. Before sending, the CLI and the app list the criteria as "Not met" (the verifier found them unmet) or "Never checked" (verification did not finish, for example at a deadline). The conditions are `acceptRefusal` in `packages/protocol/src/goal/acceptance.ts`, which the reducer applies too: a goal with a task not succeeded, work not merged or a recovery open is refused, so retry or recover it first.
  - It cannot be undone. The goal becomes `completed` with `accepted` (note, the failure it had, and `app` or `cli`) and each waived criterion marked `waived`; the `goal.accepted` event keeps the same record. Nothing runs or merges: review and merge the integration branch yourself, as after any completion. The chat that started the goal is told; the Lead, stopped at the failure, is not.
  - Only a person accepts. A request with an agent id is refused, and `paseo goal accept` refuses to run when `PASEO_AGENT_ID` is set. As with recovery, an agent that unsets the variable gets through, because a local credential cannot tell a person from an agent ([permissions](permissions.md)). There is no MCP tool for it.

- **Settings.** `paseo goal config <id>` (`goal.update_config`) changes a managed goal's settings in any state but archived: `onPermissionRequest`, `notifyLead`, `leadInterventions`, `autoApprovePlan`, `requireHumanApproval`, `testCommand`, `maxParallel`, `maxAttempts`, `maxReworkRounds` and every `limits` field. The flags are those of `goal create`; `none` clears an optional one, so its default applies or the cap is removed. Providers, models, thinking, `cwd`, `branchPrefix`, `allowedProviders` and the objective are fixed; rename changes the title. Changes are checked as on create (ranges, a deadline in the future when it changed, `auto` against the role providers) and recorded as one `goal.config_updated` carrying the whole new config; the reducer refuses one that touches a fixed field. A live goal reads its settings at the moment it uses them: running agents switch mode for a new permission policy (see [Security model](#security-model)), the next turn gets the new run timeout, the next run its mode, the next launch the new `maxParallel`, run limit and budgets. The goal-time limit and deadline are re-armed at once. Turning on `autoApprovePlan` while a plan waits approves it; `requireHumanApproval` applies to reviews that finish afterwards. A limit lowered below what the goal has used is accepted, and the next check ends the goal as it would have at that limit: the next launch for runs and budgets, the re-armed timer for time. Raise a limit on a failed goal, then retry. The same settings again record nothing.
- **Revise the plan.** `paseo goal revise <id> --file <path>` (`goal.plan.revise`) changes an executing goal's pending, failed and cancelled tasks; the command prints the revision's status and exits 1 when it was rejected. What a revision may do is checked in `packages/server/src/server/goal/plan-revision.ts`. Two rules surprise people: a desired plan (`tasks`) must list every pending, failed or cancelled task or name it in `remove`, since leaving one out is an error, not a deletion; and a task id stays taken once it ran or was removed, because run and event ids derive from it. Who proposes decides approval. With no agent id it is a person's revision and applies at once. The Lead revises with the `goal_revise_plan` MCP tool, or with the command from its shell, which sends `PASEO_AGENT_ID`; it waits for `paseo goal approve-revision <id>` or `reject-revision <id> [--message ...]` unless `autoApprovePlan` is on. Any other agent id is refused, so a person typing in an agent's shell passes `--as-person`. While a revision is pending, the tasks it changes do not start and the goal neither verifies nor fails for being stuck. While the Lead is deciding about a failed task (below), its own revisions are refused with "answer the decision prompt"; yours are not.
- **Lead decisions.** With `leadInterventions` on, a failed task asks the Lead before anything else happens to it when its run hit the time limit, when it failed for the second time, or when it used its last attempt. New goals have it on; turn it off with `--no-lead-interventions` on `goal create` or `goal config`, and failures are retried as before. The Manager waits until the Lead is idle, so a chat a person is having with it is never interrupted, then asks in a turn of its own: the task table, the run errors, and a summary of what the failed run left in its worktree (diff stat and status, read before the worktree is archived; a failure found after a restart has none). The Lead answers in that reply. `continue` retries the task as planned; on the last attempt it lets the task fail, and the goal fails as it would have. `give_up` fails the goal at once with the Lead's reason, stopping work still running. `revise` proposes a plan revision that must replace or remove the task; it applies at once under `autoApprovePlan`, otherwise it waits for your approval, and a rejection counts as `continue`; it is not offered once the plan was revised 20 times or verification started. The Lead has 15 minutes, and a decision turn a person interrupts is asked again within them. With no answer by then, a Lead that cannot take the turn, or two answers the Manager cannot use, the Manager goes on as with `continue`, cancelling only its own turn, never one a person started. The Lead is asked at most twice about one task plus once for its last attempt, and at most four times per goal; a retry or recovery that reopens the goal starts these counts again (each intervention records the goal's `reopens` as `epoch`). One decision is open at a time: a task that fails meanwhile stays failed and is asked about next, and nothing is asked while a revision waits for approval. You win: `retry` of the task or your own revision of it ends the decision and cancels the Manager's turn. While a decision is open, its task does not start, the goal neither verifies nor fails for being stuck, and notices to the Lead wait until the decision turn ends. The turns count as the Lead's usage. Each decision is an `intervention.requested` and `intervention.resolved` pair in the log.
- **Lead check-ins.** Under the same setting, the Manager also asks the Lead about a worker that is still running, when its run nears its time limit or its timeline stops moving while no tool call runs. The rules and their thresholds are in `packages/server/src/server/goal/run-watcher.ts`. While runs are healthy nothing else happens: no Lead turn, no git. The Lead sees the run's time, its recent activity and what it changed so far, the worker's text quoted as data, and answers `ok`, `nudge` or `stop`. A nudge is steered into the worker's running turn as a message from the Lead; it never replaces the turn, so work in progress is not lost, and a provider that cannot take a message mid-turn records it as `ok` with a note. `stop` is offered only near the time limit, since stopping a run that is merely quiet would throw work away on a guess; the run fails with `Stopped by the Lead: <reason>`, which counts as a failed attempt and wakes the Lead as a decision above (`lead_stopped`) while the wake-up caps allow. A check-in is skipped, not queued, while the Lead is in a turn, so a person's chat is never interrupted and a stale question is never asked later; it is also skipped while a decision about a failed task is open or due (those come first), while a revision is pending, and near a budget. Check-ins count as the Lead's usage and are capped per run and per goal, counted again after each reopen. Turning `leadInterventions` off stops new check-ins; the answer to one already open is recorded and does nothing to the run.
- **Cancel** is final. It is the stop: a live goal must be cancelled before it can be archived or deleted.
- **Rename and priority.** `goal.rename` and `goal.set_priority` work in any state, ended goals included, and record `goal.renamed` and `goal.priority_set`. A title is trimmed and must not be empty; there is no length limit, as on create. Priority is `low`, `normal` or `high`; a goal without one is `normal`, and `goal.create` takes it too. Priority does two things and no more: `goal.list` returns higher priority first (then oldest first), and when the daemon's worker slots (`daemon.goals.maxConcurrentRuns`) are full, a freed slot goes to the highest-priority executing goal with a ready task, ties to the older goal. It does not pre-empt a running task, reserve slots, or change the Lead, reviews, merges, budgets or notifications, none of which wait for a slot. Setting the current title or priority again records nothing.
- **Archive.** `goal.archive` hides an ended goal from `goal.list` and sets `archivedAt`; `goal.unarchive` sets it back to null. A live goal is refused. An archived goal keeps its log, stays readable with `goal.inspect`, and can be acknowledged, but a failed one must be unarchived before a retry can reopen it. Archiving twice returns the goal unchanged.
- **Delete.** `goal.delete` removes an ended goal for good; a live goal is refused, and so is one whose agents are still stopping. The daemon does not ask for confirmation: the app and `paseo goal delete` do (the CLI needs `--yes` without a terminal or with `--json`). Deleting a goal that is already gone succeeds with `deleted: false`. See [Operations](#operations) for what is removed and what stays; the response lists what stays as `retained`.
- **Acknowledge.** `paseo goal ack <id>` (`goal.acknowledge`) dismisses an ended goal so it stops asking for attention. It records a `goal.acknowledged` event and sets `acknowledgedAt`, so the mark survives a restart. It changes nothing else: the status stays, and a failed goal can still be retried. A retry or recovery that reopens the goal clears the mark, and so does a recovery that ends without reopening it, so that ending needs attention again and can be dismissed again. A live goal cannot be acknowledged; acknowledging twice returns the goal unchanged.

Gate each on its own `server_info.features` flag: `goalControls` for pause, resume, retry and plan rejection, `goalAcknowledge` for acknowledge, `goalBudgets` before sending `limits.maxTotalTokens`, `limits.maxCostUsd` or `limits.deadlineAt` (an older daemon drops them silently), `goalThinking` before sending any thinking field (the client refuses them without it, since an older daemon would drop them), `goalUpdates` for pushes, and `goalManagement` for rename, priority (on create too), archive, unarchive, delete and the `goal.list` filters, `goalConfigEdit` for settings changes, the `auto` policy (the client refuses it without the flag, since an older daemon's schema rejects it) and reopening a planning failure, `goalUsageBreakdown` for usage per role and per agent, `goalIntegrationRetry` for retrying a failed merge (an older daemon refuses that retry), `goalPlanRevision` for plan revisions and a task's `runTimeoutMinutes` (the client refuses both without it; an older daemon would drop the timeout silently), `goalLeadInterventions` before turning `leadInterventions` on (the client refuses it without the flag, since an older daemon drops it and never wakes the Lead), `goalTimeBase` before sending a retry's `timeMode` (the client refuses it without the flag, since an older daemon drops it and refuses the retry), `goalRecovery` before starting a recovery or sending `guidance` on a retry (an older daemon refuses the one and drops the other), `goalReworkRetry` before offering a retry or recovery of a goal with a failed rework (an older daemon refuses it), `goalAccept` for accepting a failed goal as is (an older daemon refuses it; an older client is not sent `goal.accepted` and sees an accepted goal as plain completed, its waived criteria unverified), `goalUserWait` before sending `limits.userWaitMinutes` (the client refuses it without the flag, since an older daemon drops it and counts waiting toward the time limits; an older client is not sent the `wait.*` events), and `goalVerificationRecovery` for wording that says a recovery can add fix tasks after a failed verification (an older daemon's Lead is never offered that). The daemon records `leadInterventions: true` on create when it is unset; a goal stored without it reads as off. An older daemon ignores the filters and has nothing archived, so the client refuses filters without the flag. An older daemon also records nothing for a goal created without `onPermissionRequest`, which it runs as `fail`.

`describeGoalWaitingOn` in `packages/protocol/src/goal/waiting-on.ts` names what a live goal is waiting on (plan approval, a held change set, a plan revision held for approval, the Lead's decision about a failed task, running tasks, review, merge, retry, verification, or a pause); the CLI and the app both use it. It returns an English `label` for the CLI and a translation `key` (`goals.waitingOn.*`) with `params` (`count`, `ids`, `title`, `tasks`) for the app. Use `count` for plural forms.

## Watching goals

`goal.list` returns every goal that is not archived, higher priority first, with its `usage` and a `progress` count (`tasksTotal`, `tasksDone`, `tasksFailed`, `tasksRunning`), enough for a list row without `goal.inspect`. In `goal.list`, mutation responses and `goal.update`, revisions other than the pending one come with `ops: []` (left out, not empty) and interventions without their work summaries and nudge messages; `goal.inspect` carries them in full. `summarizeGoalProgress` in `packages/protocol/src/goal/progress.ts` computes the same counts for a daemon that predates `progress`.

The request takes optional filters, combined with AND: `query` (case-insensitive substring of the title, objective or id), `status` and `priority` (lists; a goal without a priority matches `normal`), `cwd` (the goal's `config.cwd`, compared exactly; manual goals have none) and `archived` (`exclude`, the default, `only` or `include`). `includeArchived: true` is shorthand for `archived: "include"`; `archived` wins when both are sent. A client that sends no filter, an older one included, gets every goal that is not archived. There is no pagination.

To be told about changes, subscribe to the `goal.update` session event (`session.events.set_subscription.request` with `events: ["goal.update"]`, or `observeGoalUpdates()` in the client). Each `goal.update` carries one goal in the shape `goal.list` returns. The first change to a goal is sent at once; changes in the next 250 ms are folded into one push of the latest state. Only connections that subscribed get it, and only with the `automation.manage` permission. Keep polling `goal.list` as well, at a slower rate: a push missed across a reconnect is not replayed. Archived goals are pushed like any other, so filter them out of a list that hides them. When a goal is deleted, one last `goal.update` carries its final state with `deleted: true`; drop it from your list. A change still waiting out its 250 ms window when the goal is deleted is not sent.

The reducer records when each stage started and ended, from the events alone, so replay gives the same times and older logs gain them too. A change set carries `reviewStartedAt` and `reviewedAt` (left `in_review` with a verdict), `mergeStartedAt` (first entered `integrating`) and `mergedAt`. The goal carries `verifyStartedAt`, the moment every task succeeded and every change set settled, and `verifiedAt`, when the last criterion was verified. Each is absent until its stage is reached.

## Usage and budgets

The Manager records one `usage.recorded` event per agent turn: Lead, workers, reviewers and the verifier. It holds what the provider reported for the turn, or nothing, plus a reviewer's `changeSetId` and the agent's `thinking`. The reducer adds each turn up four ways:

- `usage` on the goal: every turn (`inputTokens`, `cachedInputTokens`, `outputTokens`, `totalTokens`, `costUsd`, `reportedTurns`, `totalTurns`, `costReportedTurns`, `tokenReportedTurns`).
- `usage` on each worker run.
- `usageByRole`: the same totals per role, a role absent until one of its turns is recorded.
- `usageBreakdown`: one entry per agent with its role, task, run or change set, provider, model, thinking and totals. Retries and reworks start new agents, so they get their own entries. The provider and model come from the run, or from the role's provider in the goal's config, so older logs are broken down too. The breakdown keeps the 200 most recently active agents; `usageBreakdownTruncated` counts the ones dropped, which still count in `usage` and `usageByRole`.

Tokens mean the same for every provider:

- `inputTokens` is fresh input: tokens the model read that did not come from the prompt cache. Cache writes count here.
- `cachedInputTokens` is input read from the prompt cache. It is tracked and shown, and left out of `totalTokens`.
- `totalTokens` is `inputTokens` + `outputTokens`, the number `limits.maxTotalTokens` is checked against. Cache reads are left out because a long agent re-reads its context on every model call, so they would dwarf the work done, and they cost a fraction of fresh input.
- Every field covers the whole turn, subagents and every model call included.

Providers do not report this way, so the daemon converts at the boundary (`toTurnUsage` in `goal/goal-ports.ts`). Claude reports the process's running totals in `modelUsage` and `total_cost_usd`; its adapter reports each turn's share. Codex reports its last model call, with cache reads inside input; its adapter reports the turn's growth of the thread total. OpenCode, pi and omp report session totals; the goal takes their growth since the agent's previous turn. That baseline lives in memory, so after a daemon restart a resumed session's first turn counts the session so far. Other providers (ACP agents, Copilot) are taken as reported.

The conversion applies to turns recorded from v0.13.3 on. Older events keep the numbers they were written with and replay unchanged: Codex input there includes cache reads and covers only a turn's last model call, and a Claude agent's later turns repeat its earlier cost.

Treat the totals as a floor:

- Some turns report nothing, or report after the turn has ended (pi and omp poll session stats in the background). They count in `totalTurns` only.
- `costUsd` is what providers computed; Paseo never prices tokens itself. Codex reports no cost. When `costReportedTurns` is below `totalTurns`, the cost is a lower bound, and the CLI shows it as `>=$0.53`. Show the same next to any total: "cost reported for 1 of 4 turns". `tokenReportedTurns` does the same for tokens. Both are absent from older daemons.

`limits.maxTotalTokens` and `limits.maxCostUsd` fail the goal once the reported totals reach them, and a goal over budget is not reopened. A retry never resets them, whichever time mode it chooses. Lead decision turns count too, at most four per goal, and so do check-in turns, which stop near a budget (see [Lead decisions](#control-a-running-goal)). They cannot stop a turn already running, and they never count what was not reported: a goal whose workers report no cost is held to `maxCostUsd` by its Lead and reviewers alone.

Gate the breakdown on `server_info.features.goalUsageBreakdown`. Clients without the `goal_usage_breakdown` capability get goals without `usageByRole`, `usageBreakdown` and `usageBreakdownTruncated`.

## Security model

Goals run with the `automation.manage` permission, the same as schedules. Anyone who holds it can start agents that run commands on the machine. The boundaries below limit what a goal does by accident, not what a malicious holder of the permission can do.

- **The permission policy sets the agents' mode.** Every agent works in a worktree. Under `wait`, the default, agents start in the provider's default mode (for Codex `auto-review` when its version has the auto-reviewer, else Default Permissions) and a permission request stays pending in Paseo for you to answer; `limits.userWaitMinutes` ends one nobody answers (the turn is abandoned even if the provider ignores the cancel). Under `auto`, agents start in the provider's auto mode, where a classifier or reviewer answers prompts, and anything still asked waits as under `wait`. The auto mode is picked per provider by `goalAutoModeId` in `goal-config-validation.ts`: Claude's `auto` (Auto mode) and Codex's `auto-review`, which sends eligible approvals to Codex's auto-reviewer and still asks for the rest. Codex's mode with id `auto` is Default Permissions, which asks for every command, so it never counts; a provider with no entry uses a mode with id `auto`. Goal creation and `goal config` refuse `auto` when a role provider lists no such mode, as Claude on Bedrock or Vertex and a Codex too old for the auto-reviewer; a provider whose modes cannot be read, or a task's own provider from the plan, starts in its default mode instead. Under `fail`, agents start in the provider's unattended mode (Claude's bypass, Codex's Full Access), act without asking, and a run that still asks fails. `fail` is the way to run Codex without prompts; the name is historical and the app will relabel it. `goalPermissionPolicy` in `packages/protocol/src/goal/config-bounds.ts` resolves a stored config: a goal created before `wait` became the default stored nothing and keeps running as `fail`.
- **Waiting for an answer.** An agent waits once a permission request or question has stayed pending for one poll (about a second), so a request that clears itself is not counted. A wait lasts until it is answered or withdrawn, or `limits.userWaitMinutes` passes (12 hours by default; each request gets the full allowance). While it lasts, the run's time limit is paused and resumes with the time it had left, and the goal's time limit stops counting; when several agents wait at once, the overlap counts once. `limits.deadlineAt` is a fixed time and is never pushed back. Lead, reviewer and verifier turns wait the same way as workers. A waiting worker keeps its slot under `maxParallel` and `goals.maxConcurrentRuns`, so a goal whose workers all wait starts nothing else. The Lead is not asked about a waiting run: it is never stalled or near its time limit. The allowance is read when each wait starts, so `goal config --user-wait` reaches the next request of a running turn. Past the allowance the run fails with `No answer within <n> minutes: <the request>`; it is not retried and does not wake the Lead, whatever the policy, and the goal fails with `stopped on a request (needs_permission)` once nothing else can run. A person's retry runs it again and forgives that failure. The other roles end as their failures always did, quoting the no-answer error: a reviewer's change set is rejected (`Review failed: Reviewer did not finish (failed: No answer within …)`), which is final; a verifier fails the goal with `Verification failed: …`, which a recovery with retry asks again; a planning Lead fails the goal with `Lead agent did not finish planning (failed). No answer within …`, which a retry plans again. Under `auto`, a request the provider's auto-reviewer takes more than a second to approve also counts as a wait, though no person answered it. Waits are recorded as `wait.started` and `wait.ended` events, so a replay computes the same time limits. A daemon restart ends every open wait at boot, so the time the daemon was down counts as waiting, however long, even past `userWaitMinutes` (the daemon log warns when it is); `paseo goal inspect` lists each wait and the downtime inside it.
- **A policy change reaches running agents.** When `goal config` changes `onPermissionRequest` on a goal that has not ended, the Manager switches its Lead, running workers, reviewers and verifier to the mode a new agent would start in, through the same path as the app's mode picker; the daemon log lists which agents switched, which switch next turn, and which could not be switched (that does not fail the edit). Claude agents take the new mode at once. A Codex agent in the middle of a turn keeps its old approval policy until its next turn, and a worker's run is one long turn, so a running Codex worker keeps asking: answer the pending prompt, or cancel and retry the task. A turn reads the policy on every poll, so switching to `fail` ends a turn that waits on a request, and the task retries in the new mode, since its agent started under the old policy. A pending request is not answered by the switch. Reviewers stay read-only under any mode, since that is checked on the worktree.
- **A run stopped on a request is not retried.** Unattended modes skip permission prompts, not every question: Codex in Full Access still asks with `request_user_input`, and under `fail` a run that asks ends there. The run's error says what was waiting, quoting up to 300 characters of the question or of what the permission was for: `Agent asked a question and the goal's permission policy (fail) cannot answer it: "…". Change the policy to wait or auto, or resolve what triggers the question, then retry.`, or `Agent is waiting for permission to use <tool>: "…" and the goal's permission policy (fail) cannot grant it. …`. The task is not retried while the policy is the one its agent started under, because a new worktree asks the same thing again, and a restart does not retry it either. The goal fails once nothing else can run, with `Task <id> stopped on a request (needs_permission): <error>` in its reason. A user hook is a common trigger: a hook that keeps a decision per worktree asks again in every new Paseo worktree. Answer it or change the policy with `goal config`, then `retry`, which starts a fresh attempt. Under `wait` and `auto` the question waits in Paseo like a permission, including a Codex question asked without holding the turn (`request_user_input_async`): the run waits while it is open, then for the turn your answer starts.
- **Worker status line.** Implement, read, review and rework prompts ask the worker to end its final message with a `TASK_STATUS: done` or `TASK_STATUS: blocked: <reason>` line, after any `Answer:` section (a global `CLAUDE.md` can make workers end with one, and t8 of goal 4fe24f94 put its "blocked" there in prose, which counts as no status), and not to end its turn while its own background commands still run. The format, and where in the message the line counts, is in `workerStatus` (`packages/protocol/src/goal/failure-wording.ts`). No status line means the run is judged as before; `done` is dropped from the task's report. A `blocked` run fails and is never retried on its own. With Lead decisions on, the Lead is asked first and only its continue retries the task, also after a restart. Otherwise (the Lead gives up or does not answer, its wake-ups are used up, or the task is a rework) the task waits for you and the goal fails with the worker's reason quoted first; a blocked rework rejects its change set as `rework_failed`, which retry reworks again. The status is the worker's own claim and nothing checks it. A false `blocked` costs a failed attempt and a Lead decision, or fails the goal until you retry, which forgives the attempt. A false `done` changes nothing: review, `testCommand` and the verifier still judge the work. Reviewers and the verifier answer in JSON and get no status line.
- **Read-only roles are checked, not trusted.** The Lead plans in a worktree of its own, kept while the goal runs and archived if it is cancelled or fails. A reviewer that changes the change it reviews has the changes undone and its verdict discarded. A verifier that leaves the integration branch changed or dirty has its verdict discarded and the branch reset.
- **`testCommand` is a shell command you chose.** It runs with your privileges in the integration worktree and has a fixed 10 minute limit. It is judged by its own exit, so a background process it leaves behind does not fail it, and it is killed when the goal ends or the daemon shuts down. Agent-written code runs inside it, so use a command and repository you trust.
- **Agent text is data.** Findings, test output, task reports and errors that reach another agent's prompt are quoted between delimiters that change on every prompt. That lowers the risk of prompt injection and does not remove it. An agent that reads attacker-controlled files can still be steered.
- **Plans cannot widen the goal.** A plan that names a provider outside the registered set or the allow-list is sent back. Task ids ending in `-rw<n>` are reserved. A managed goal's plan can only come from its Lead; `goal.propose_plan` is refused for it. A revision is the Lead's only when the caller's agent id is the goal's Lead; with no agent id it is a person's. The id is the caller's own claim, so it only decides approval: an agent with the CLI can already act as a person.
- **Recoveries and guidance are a person's.** The recovery RPCs, and `goal.retry` with guidance, refuse a request that carries `agentId`; there is no MCP tool for them; and the CLI refuses `goal recover` and `goal retry --prompt`/`--task-prompt` when `PASEO_AGENT_ID` is set. That stops an agent that says who it is, not one that unsets the variable. A recovery Lead with a shell can run `env -u PASEO_AGENT_ID paseo goal recover <id> --approve` and approve its own plan change: its CLI holds the same credential as your terminal, as for everything else under this permission. The control is the permission policy, which decides whether that command runs unasked.
- **Verdicts are judgments.** A reviewer or verifier records evidence, and it can be wrong. For anything that must not depend on an agent's word, put it in `testCommand`.

Not protected: network access, files outside the worktrees that the agents' mode lets them reach, and credentials in your environment. Treat a goal like a script you let a contractor write and run.

## Operations

- **State.** One file per goal, `$PASEO_HOME/goals/<goalId>.jsonl`, one event per line, fsynced on append, and the directory is fsynced when a new log is created. A torn last line from a crash is truncated on load. Do not edit these files.
- **Delete.** A deleted goal's log is first renamed to `<goalId>.jsonl.deleted` (one atomic rename, then a directory fsync), so after a crash the goal is either whole or gone. Next its timers are dropped and every worktree it recorded (the Lead's, the integration worktree, each change set's and each run's) is archived through Paseo, which removes the directory of a Paseo-owned worktree that no other workspace uses. A worktree with uncommitted changes is kept. Branches are never deleted: the integration branch holds the goal's result and the change set branches its history. Last the tombstone is removed. A start that finds a tombstone finishes the deletion. The goal id can be used again afterwards.
- **Unreadable logs.** A log that fails to replay, or comes from a newer version, makes that goal unavailable and is logged at start. Other goals and the daemon are unaffected. The file is left as it is.
- **Compatibility.** There is no migration step. Event changes are additive, and tests replay logs written by each earlier phase. A log in which a retry or recovery reworked a change set again, or a recovery added work after verification started, is set aside by a daemon older than v0.13.14, whose reducer refuses either; so is a log with a Lead decision about a blocked worker (trigger `worker_blocked`), whose trigger an older reducer does not know, and a log with `wait.started` or `wait.ended` events, which an older reducer does not know. A failed goal's `failedAt` is its `goal.failed` event's time, so an older log replays with it too; only goals sent by a daemon without `goalRecovery` lack it, and `diagnoseGoalFailure` then reads the time-limit wording of the reason. An implement task that succeeded before work capture existed cannot be recovered; its goal fails rather than completing unreviewed.
- **Worktrees.** The worktree of a failed run is archived when it fails, not after its retry backoff. Worktrees of abandoned runs, and of read and review tasks, are archived too. Worktrees of successful implement tasks, the integration worktree and the Lead's worktree are kept so you can inspect them. The Lead's worktree is archived if the goal is cancelled or fails. Archive the rest from Paseo when you are done, or delete the goal.
- **Restarts.** A graceful shutdown stops the Manager before agents close, so runs are not recorded as failures. The next start marks them interrupted and runs them again with a new run id. It asks the Lead again about a decision left open, with the 15 minutes counted from when it was first asked, and asks about a failure recorded just before the stop instead of retrying it blindly. A check-in left open ends with its run, which the start marks interrupted, so it is not asked again. So does a stop recorded just before the run's failure: the run is interrupted, not counted, and retried. A failed goal's recovery goes on from its recorded state: a recovery Lead created just before the stop but not yet recorded is found by its `paseo.goal-recovery` label and archived, then a new one is asked; an open decision is asked again within its 20 minutes, or falls back once they are over; a decided one is applied; one waiting for approval keeps waiting; and an ended one's Lead is archived if it is still there. A worktree made for a recovery Lead whose agent was never created before the stop is not found; archive it from Paseo. It also sends every notification still pending at once, for ended goals too, within the five attempts; a delivered one is never sent again. Goals from before notifications were recorded have none and are not messaged again.
- **Cancel.** `paseo goal cancel` stops the Lead, workers, reviewers and verifier, the test command and any retry backoff, and archives the worktrees of every run still in flight. Uncommitted work in those worktrees is lost.
- **Concurrency.** At most `daemon.goals.maxConcurrentRuns` worker runs across all goals (1 to 32, default 4), and `maxParallel` per goal. Set it with `paseo daemon config set daemon.goals.maxConcurrentRuns 8 --home <home>`, through `set_daemon_config_request` (`goals.maxConcurrentRuns`, gated on `server_info.features.goalConcurrencyConfig`; an older daemon drops it silently), or in the app under the host's Agents settings, Goals. It applies without a restart: a raised cap starts waiting tasks at once, a lowered one lets running tasks finish and starts nothing new until the daemon is under it. Every run is a coding agent, so raise it only as far as the machine's CPU and memory and the providers' rate limits allow. The Lead is told the cap and the goal's `maxParallel` when it plans. The Lead, reviews, merges and verification are not counted. A task waiting out a retry backoff holds no slot. When a run ends, executing goals are offered the freed slot in priority order, then oldest first. Priority only orders that hand-off: a goal that becomes ready while a slot is already free takes it, whatever its priority.
- **Logs.** The Manager logs under the `goal-manager` and `change-set-pipeline` modules in `daemon.log`.

## Supported workflows

- Feature or fix work on a git repository that decomposes into tasks, with a test command that can judge a merge.
- Mixed providers: a planner on one, implementers on others, an independent reviewer on a third.
- Unattended runs bounded by time and run limits, and runs gated by your approval of the plan, each change, or both.

Not supported: goals without a git repository, merging into your branch or opening a pull request, re-planning around a failed criterion (the goal fails), and multi-repository goals.

### In the app

- **List.** Goals waiting on you come first: a plan or a change set held for approval, or a failure. The toolbar has two blocks: the search field and filters wrap inside the first, and New goal stays at the top right at any width (on a phone the filters wrap under the search field). Each filter is an icon button that opens its menu: status (Action, Running, Done, All), project (once the goals span more than one), priority and sort, plus Show archived as an icon toggle. A filter away from its default is highlighted and carries a dot; the sort counts as changed only away from the default order. The status button always carries the count of goals waiting on you, so filtering never hides it. Each row names the goal's project and directory, says what the goal waits on, and shows the host's `progress` counts and its usage (against the cap when one is set). A total that only some turns reported is prefixed `≥`, and a host that counts cost reports and got none says cost is not reported; this is the rule `paseo goal ls` prints as `>=$0.53` and `no cost`. With no goals, the screen offers templates that fill the create form.
- **Search, priority, sort, archived.** Search matches the title, objective, id and project name. It runs in the app on the full list, not through `goal.list`'s `query`: the list is never paged, and the host does not know project names. With `goalManagement`, the priority filter and Show archived appear; Show archived fetches `archived: "include"` under its own query key and lists archived goals in their own group, muted. The sort (priority, recently updated, newest, name) orders goals inside each group and is remembered per device (`goal-list-preferences-store.ts`). An archived goal never waits on you, so it leaves the Action filter and the badge.
- **Manage.** Each row has a kebab (hover-revealed on web, always shown on touch and compact layouts), and the detail header has the same menu, built by `goalAvailableActions` in `packages/app/src/goals/goal-management.ts` from the goal's state and the host's flags: Rename, Priority, Edit settings, Pause or Resume, Retry, Dismiss, Archive or Unarchive, Cancel goal, Delete. Archive and Delete appear only on ended goals and not while a recovery is open; cancel a live one first. Retry is hidden on an archived goal and while a recovery is open. Cancel and Delete ask first; Delete says branches are kept and, when the host retained anything, lists it in a toast. Priority changes show at once and roll back if the host refuses. A `goal.update` with `deleted: true` drops the goal from every cached list.
- **Goals waiting on you (Action).** On hosts with `goalUpdates`, `useGoalUpdates` applies each `goal.update` to the cached `goal.list`, so the badge and toasts react at once; polling drops to every 60 seconds to repair a push missed across a reconnect. Other hosts are polled: `GoalAttentionWatcher` every 15 seconds, the Goals screen every 5. A push older than the cached goal (lower `lastSeq`) is dropped, and a poll never overwrites a newer pushed goal. The sidebar badge counts plans, change sets and plan changes held for approval (a running goal's or a recovery's), not failures. While a recovery decides or applies, a failed goal leaves the Action filter, is listed under Running instead of Done, and shows Recovering. A recovery that ends without reopening the goal is a new failure: the goal asks again, even if you dismissed it before the recovery started. A goal that starts waiting shows a toast naming what it waits on, again for each later plan change; the first list after launch stays quiet.
- **Dismiss.** With `goalAcknowledge`, an ended goal's detail offers Dismiss, and so does a failed goal's list row; neither does while a recovery runs. A dismissed failure leaves the Action filter but stays under All and Done, marked Dismissed. A retry clears the mark, and so does a recovery, whether it reopens the goal or ends without doing so; a goal still failed is then back in Action and can be dismissed again.
- **Detail.** The stepper, the banner and the progress panel all derive from the goal state in `packages/app/src/goals/`, with the phase taken from `describeGoalWaitingOn`. A Team section lists each role's provider value and thinking from the config (`goalTeam`); each task row shows the thinking its latest run started with (`AgentRun.thinking`). Held change sets get Approve and Request changes. Each task opens the agent of its latest run. Pause, Resume, Send back (plan rejection) and Retry appear only with `goalControls`. A goal that failed before it had a plan offers Retry planning instead, and only with `goalConfigEdit` too, since an older daemon refuses that retry. A goal whose merge failed offers Retry merge, only with `goalIntegrationRetry`, and its failure banner says to fix what the error names in the integration worktree first (`goalControlsAvailable` in `goal-phase.ts`); a change set rejected by review hides Retry. When the failure was a permission request or a question (`needs_permission` in the reason, `goalFailedOnPermission`), the detail says to pick Ask me or Auto mode in the settings first, and for a question (`goalFailedOnQuestion`) to remove what makes the agent ask; the reason quotes the question. Retrying unchanged fails the same way. The activity feed shows settings changes, planning restarts, merges retried, plan changes, the Lead's decisions about failed tasks and its check-ins on running ones, and recoveries. A Plan changes section lists plan changes made after approval: the pending one with who proposed it, its reason, and each task added, changed (with what changes) or removed; decided ones with their status and reason. Approve and Reject (with an optional message for the Lead) need `goalPlanRevision`. A decided plan change from `goal.list` or a mutation response comes without its ops, so the section shows ops only when the payload has them; the detail reads `goal.inspect`, which has them all, and a mutation's response updates only the cached lists, never the detail. Each task row shows your instruction and the recovery Lead's advice for its workers; a text a list payload cut short is marked so. Waiting-on text is translated from the `goals.waitingOn.*` key and params; the protocol's English label is only the fallback. Locales whose plural rules need more forms than one and other (Russian, Arabic) list them next to a base key, which `TranslationResources` allows for `goals.waitingOn` and the diagnosis counts.
- **Recover.** With `goalRecovery`, a failed goal's detail shows a Diagnosis card, computed in the app with `diagnoseGoalFailure` and `goalActiveMs`: why it stopped, whether you must act, each failed task's cause and what it blocks, and each limit that leaves no room with the smallest value that would, with one Edit settings button for them all. A live recovery's time mode counts as chosen, so a passed time limit it restarts no longer shows as blocking. Recover sits in the failure banner, as Recover again once the goal has used one; when all 3 are used it stays there disabled, with a line saying so. When every task succeeded and a criterion is not verified, the banner, the sheet and the diagnosis say the Lead can add fix tasks and that every criterion is verified again once they are merged; only with `goalVerificationRecovery`, since an older host lets the plan only lose tasks, which its diagnosis still says. With no recovery left the diagnosis says to start a follow-up goal instead. From `verificationRound` 1, the criteria section says verification restarts after the fix tasks, and then that the round checks every criterion again; the badges show only the current round. The activity feed keeps each round's verified line for the same criterion and names the round from round 1, read from the event id's `:v<round>` suffix. It opens a sheet with how many recoveries are left, an instruction for the goal and one per failed task (prefilled with your current ones; emptying a field clears it) and, when the time limit passes within the Lead's 20 minutes, the Fresh or Remaining choice the retry sheet offers, preselected to Remaining when that leaves at least 30 minutes and to Fresh otherwise. When the last recovery ended, its Lead's reason shows above the fields as read-only text. It is never copied into a field: what you send stays your own words, which the Lead and the workers treat as authoritative. The sheet reads the goal once when it opens, and closes if Recover goes away meanwhile. While the recovery runs, a Recovery card shows its state and the Lead's decision (advice per task, the plan change, or what a person must do), Approve and Reject for a plan change, and Cancel except while the decision is applied; Retry, Archive, Delete and another Recover are hidden, and the detail keeps polling though the goal is failed. The row menu has no Recover.
- **Failure reason, once.** A recovery that ends without reopening the goal rewrites its reason to `Recovery needs a person: <the Lead's reason>`, and the same text is in the recovery and the feed. The banner shows only the reason's first sentence; a bare `.` never ends it, since reasons quote paths such as `updater_module.c:1301-1310`. After a recovery that needs you, the banner is titled Recovery needs you and the sentence is the Lead's own, without the prefix. Show details opens the full reason, the failure the recovery started from (shown nowhere else) and the criteria not verified. The Recovery card keeps its status and the decision, with the reason cut to its first sentence and More. A feed line with a long detail shows the detail's first sentence and opens in place on tap.
- **Follow-up goal.** A failed managed goal's banner offers Start a follow-up goal. It opens the create form with the title `<title> — follow-up`, the same project, providers, thinking, test command and settings (your last goal's remembered ones never fill in for them), and no deadline. Its criteria are the ones not verified, also listed in the objective; when every criterion was verified and the goal failed for another reason, all of them are asked again. It builds on the failed goal's integration head, or the commit it started from when nothing merged, and the form says which goal, commit and branch. Start from the project's HEAD instead, picking another project or moving the form to another host drops that commit. The objective takes no text from the Lead.
- **Edit settings.** With `goalConfigEdit`, the detail header and the row menu open a sheet with the settings `goal.update_config` takes, for any goal but an archived or manual one. It sends only the fields you changed. While it is open, a config pushed by the host updates the fields you have not touched and keeps the ones you have. The sheet says the new values apply from the next turn or run, and that an agent already running keeps its mode.
- **Progress is an estimate.** The percent weights each implement task as half done when its run succeeds, three quarters when its change is approved, done when merged; planning and verification bracket the tasks. Time left needs two finished tasks and spreads the fastest and slowest over `maxParallel` (at most the daemon's default cap of 4; the estimate does not read the host's cap), then adds the review, merge and verification still ahead, sized from the stage times this goal already recorded. On a host without stage times, or before a stage has finished once, that stage adds nothing, so read the range as a floor. Task bars show each change set's review and merge windows, and verification gets its own bar.
- **Usage.** A Usage section under the progress panel holds tokens and cost for the whole goal, with the cap bars. Tokens are input plus output; input, cache reads and output are listed under the total, using the meanings in [Usage and budgets](#usage-and-budgets). A total that only some turns reported reads "At least" with "cost reported for 1 of 4 turns" under it; none reported reads "Not reported", never `$0.00`. Token counts use the CLI's one-decimal format so the two can be compared. With `goalUsageBreakdown`, By role and By agent fold out: one line per role and per agent, newest first, named by task title or run or change set id, with provider, model and thinking, and "Older agents not shown" when the host dropped some. Wide layouts align the numbers in columns; compact ones fold them under the title. An older host gets the totals and a line asking to update it.
- **Project.** A managed goal starts by picking a project: the host's git projects, most recently used first, or another folder (the desktop folder dialog when the host is this computer's daemon, a typed path otherwise). The form picks for you in this order: the directory it was opened from (the chat, or the workspace you were in, kept exactly, so a worktree's branch is what the goal builds on), your last project on that host, the host's most recently used project. The form asks the host for the folder's checkout status (`checkout_status_request`), refuses one that is not under git, and shows the branch the goal will build from. It cannot show the base commit: the status carries no head commit. A goal's project is named by matching its `cwd` against the host's project roots and workspace directories; a folder the host does not list shows under its own name. With more than one connected host that runs goals, the form also picks the host; a goal started from a chat stays on the chat's host so the outcome can be posted back.
- **Create form.** The objective is the only text you must write when the goal is manual; the title defaults to its first line. Careful, Balanced and Turbo fill every advanced setting; Balanced is the daemon's defaults. Careful, and the Refactor with review template that uses it, turn on Ask me before changes are merged (`requireHumanApproval`), the only setting that holds a change set in `awaiting_human`. The form opens with your last goal's settings, so after one Careful goal every new goal holds its changes too until you turn the switch off; the outcome summary at the end of the form says which applies. A switch turned off on a running goal does not release changes already held: approve them. Number fields take typed values with units (`90m`, `1.5h`, `250k`, `$12.50`) or a horizontal drag on their handle; on web, arrow keys step and Shift steps further. Only the handle takes the drag, so the form still scrolls vertically on touch. On a phone the cost cap opens the decimal pad and every other field the number pad, which has no letters, so you type a bare number in the field's base unit (minutes, seconds, tokens). A lone comma that is not a thousands group is the decimal point (`2,5` is `$2.50`), since a comma-locale decimal pad types one. The iOS number pads have no return key: tap outside the field to close the keyboard; the value is already committed while it is valid. Each value a drag lands on gives a selection haptic, and a screen reader adjusts the handle with increment and decrement. Ranges come from `GOAL_CONFIG_BOUNDS`: a value outside one shows an error and is clamped when the field loses focus. An empty budget means no limit. The permission choice is Ask me (the default, `wait`), Auto mode (`auto`: Claude Auto mode, Codex Auto-review; shown only with `goalConfigEdit` because an older daemon's schema rejects it) and No prompts (`fail`: agents start unattended, so they do not ask, and a run that still asks fails); the hint warns that No prompts lets agents run commands and use the network unchecked. The Edit settings sheet says a change reaches running agents too: Claude at once, Codex after its current turn. A refusal from the host shows in the form. The form remembers your last managed goal per host (project, providers, settings) and offers its settings as Mine; it never overrides the directory the form was opened with; the test command comes back only for the same directory. The budget inputs appear only on hosts with `goalBudgets`, since an older daemon would drop the caps silently. With `goalThinking`, each role's model picker is followed by a Thinking picker filled from that model's `thinkingOptions` (no model means the provider's default model, as the daemon picks it); it is hidden when the model offers none. The reviewer and the verifier run on the review provider, or the Lead's when none is chosen, so their pickers follow that model. Changing a provider or model drops a level the new model does not list. Model default sends nothing. Presets leave thinking alone; the remembered last goal carries it. Optional fields equal to the daemon's default are left out of the config, except `onPermissionRequest`, which is always sent: an older daemon would run a goal without it as `fail`. The form memory is at version 2, which reads a remembered `fail` as `wait`, because `fail` used to be the form's default and was stored whether or not you chose it; if you did choose it, choose it again. The form does not set per-task providers or thinking, `verifyProvider`, `branchPrefix` or `limits.deadlineAt`.

### From a chat

In an agent chat, `/goal <objective>` or **Start goal from this chat** in the tab's menu opens the create form with the goal run by agents, the chat's working directory, and the chat's provider for the Lead and tasks. Without text after `/goal`, the objective is the chat's last message. The goal gets its own Lead; the chat stays as it is and receives the outcome, because the form sets `originAgentId` to the chat.

## Known limits

- Setup scripts run in every goal worktree. Anything setup leaves uncommitted in the integration worktree is reset before the first merge; setup output in a task's worktree is committed with its work and goes through review.
- The reviewer check sees `HEAD` and uncommitted files in the author's worktree, not ignored files or other refs. Reviewers legitimately run tests that create ignored files, and every agent shares the repository's refs, so a ref snapshot would flag other agents' own commits; neither check is done.
- A reviewer or verifier interrupted by a restart is not cancelled before its replacement starts. If a provider keeps agent processes alive across a daemon restart, two could briefly work on one worktree.
- Verification runs after all changes are integrated, and again in full after a recovery adds work. Each round is one more verifier turn.
- A crash after a merge commit but before it is recorded leaves that commit on the integration branch; recovery resets the branch and merges again.
- If `cwd` is a subdirectory of the repository, git commands run in that subdirectory of each worktree.
- Quoting agent text in prompts does not stop prompt injection.
- A notification is sent at least once, not exactly once. If the daemon stops after the agent layer accepted it but before that was recorded, the next start sends it again. A crash after a goal ends but before its notifications are recorded loses them.

### Native checks

The Goals UI was built and checked on web only. These need a person with a real iOS and Android device; the Maestro flows in [packages/app/maestro/README.md](../packages/app/maestro/README.md#goals) automate the parts a script can see.

- **Keyboard in sheets.** In the create form and Edit settings, focus the objective, a number field low in the sheet, and the cost cap. The sheet extends above the keyboard and the focused field stays visible. Tapping outside a field closes the number pad on iOS. With the keyboard up, Create and Save respond to the first tap.
- **Number pads.** Counts and durations open the number pad, the cost cap the decimal pad. With the device region set to one that uses a decimal comma (German), `2,5` in the cost cap reads back as `$2.50` after blur.
- **Drag versus scroll.** A sideways drag on a handle changes the value and neither scrolls the sheet nor moves it; a vertical drag starting on the handle scrolls the sheet; pulling the sheet down from its header still closes it. A slow diagonal drag does one or the other, never both. Each new value ticks once, the range ends do not tick, and a tap on the handle does nothing.
- **Back (Android).** Back closes an open menu or sheet first, then returns from a goal's detail to the list, then leaves Goals.
- **Safe areas.** On a notched iPhone and on Android with gesture navigation, the sheet footers (Create, Save) sit above the home indicator, and the Goals header clears the status bar.
- **Touch targets.** The row kebab, the detail menu and the handles open or drag on the first try with a thumb; tapping a row's kebab never opens the row.
- **Long text.** A long title wraps in the detail header without pushing the badges or menu off screen, and is truncated to one line in the list.
- **Screen reader.** With VoiceOver and TalkBack, a handle reads its label, value and hint; swipe up and down (iOS) or the volume keys (TalkBack) step it; By role and By agent announce expanded and collapsed.
- **Usage and times.** Token and cost numbers, relative times and activity timestamps format in the device language (Hermes `Intl`).

## Changing goals

- Add fields and event types; never change or remove the meaning of an existing one. Old logs must still replay, and the compat test must cover the change.
- Put every rule the Manager relies on in the reducer. The Manager can then be wrong without corrupting a goal.
- Use commits, not branch names, for anything stored. Paseo can rename a worktree's branch.
- Keep new RPCs under the `goal.*` namespace and gated on `server_info.features.goals`, or on the flag added with them.
- A new event type breaks an older client's strict event union. `goal-session.ts` leaves such types out of `goal.inspect` for clients without the matching capability (`goal_control_events` covers `goal.paused`, `goal.resumed`, `goal.retried` and `usage.recorded`; `goal_acknowledge_events` covers `goal.acknowledged`; `goal_management_events` covers `goal.renamed`, `goal.priority_set`, `goal.archived` and `goal.unarchived`; `goal_integration_retry` covers `changeset.integration_retried`; `goal_plan_revision` covers `plan.revision_proposed`, `plan.revision_approved` and `plan.revision_rejected`, and without it the goal payloads leave out `planRevisions` and `interventions`; `goal_lead_interventions` covers `intervention.requested` and `intervention.resolved`, and without it the goal payloads leave out `interventions`; `goal_recovery` covers `recovery.started`, `recovery.decided`, `recovery.resolved` and the Lead's recovery prompt (`intervention.requested` with trigger `recovery`), and without it the goal payloads leave out `recovery`, `recoveries`, `guidance` and recovery interventions; `goal_config_edit` covers `goal.config_updated` and `goal.reopened`, and without it an `auto` policy is sent as `wait`, in `goal.list`, `goal.inspect`, mutation responses and `goal.update` pushes; without `goal_usage_breakdown` the same payloads leave out the usage breakdown); add yours there. A new variant of a closed union breaks the same parsers: a new revision op kind (`PlanRevisionOpSchema` in `packages/protocol/src/goal/types.ts`) needs its own capability, or a payload that leaves such revisions out for older clients, since it appears in `Goal.planRevisions` as well as in events.
- A new push message must reach only clients that asked for it. Deliver it as a session event subscription, as `goal.update` is, and return false for it in `legacyWantsEvent` in `session.ts`.
