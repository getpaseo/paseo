## M-SERVER-1 — Editing a working file disables review on an unchanged committed chapter diff

**S2/F2 → P2; confidence 100; single-user; gate: blocks** preserving the existing Chapters inline review workflow during this integration. Frequency is conditional on reviewing a base comparison containing a TypeScript file and editing that file locally; prevalence is unknown. One occurrence is recoverable, but it disables comment editing and directs the user toward unnecessary regeneration.

**Invariant:** Chapters freshness and inline-review availability track the selected comparison's actual changes, not whether language navigation can currently operate on the working file. Basis: the base comparison resolves to base→HEAD in `packages/server/src/utils/checkout-git.ts:3311`, and existing `chapterFingerprint` explicitly excludes presentation tokens; the Chapters service's snapshot/cache and explicit-regeneration behavior are covered by its existing tests.

**Sites and mechanism:** The incoming call in `packages/server/src/utils/checkout-git.ts:3455` attaches `targetContentId` only when the working file still matches the committed target. `packages/server/src/server/code-language/diff-snapshot.ts:53-58` omits that field after a local edit. The retained branch's `packages/server/src/server/chapters/service.ts:33-34` hashes every file property except `tokens`, so this eligibility-only change alters the fingerprint while the base→HEAD hunks remain identical. `packages/app/src/chapters/use-chapters.ts:83` marks the story stale; `packages/app/src/chapters/panels.tsx:139` sets `reviewActions.readOnly` and drops its editor. This is introduced by the merge: HEAD has Chapters but no targetContentId producer; incoming has that producer but no Chapters consumer.

**Concrete scenario (not executed):** Generate a base-comparison story for a committed TypeScript change while its working file matches HEAD. Edit that same file without committing. When Chapters next refreshes (periodic refresh is 15 seconds), the new snapshot omits targetContentId but retains the identical committed diff. The old story becomes stale and inline comments become read-only. Restoring the working file reverses the false staleness; regeneration also works but needlessly invokes the helper and changes the review draft fingerprint.

**Counterexamples inspected:** Non-TypeScript files receive no identity, so this interaction does not affect them. Real base/HEAD content changes should still invalidate chapters. The code-language identity omission is intentional and tested in `diff-snapshot.test.ts` (HEAD mismatch case); disabling that guard would be wrong. Code-language queries independently check file content at `code-language/session.ts:221-237`, so excluding this metadata from the chapter semantic fingerprint does not weaken query safety. No automatic regeneration loop is claimed: Chapters retains old stories until explicit regeneration.

**Fix direction:** Exclude `targetContentId` from chapter fingerprinting like `tokens`; retain the metadata in files for language actions and keep the query freshness checks. A focused regression should prove identical comparison/files hash equally with this field present/absent/changed, while changed hunks still differ. A service-level or real-Git base comparison check should establish unchanged story freshness after working-file edits. These checks are proposed, not executed.
